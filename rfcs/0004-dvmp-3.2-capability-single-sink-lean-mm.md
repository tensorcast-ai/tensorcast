# RFC 0004 — DVMP 3.2: Capability‑Driven Direct Writes, Single Sink Contract, Lean Memory Manager

Status: Proposal
Date: 2025‑08‑08
Owner: StepCast Core
Depends on: 0001 (DVMP 2.0 + Unified Loader)
Supersedes: 0002, 0003

## 0. Summary

This RFC consolidates and refines the ideas in 0002 and 0003 after a deep review of the current code paths. It proposes concrete, low‑risk edits that improve generality, maintainability, and performance while reducing conceptual surface area.

It focuses on three changes and their supporting details:

- Standardize on a single sink contract (`PositionedSink`) for loader data paths; treat `pump()` as a thin convenience over a single range in `pump_ranges()`.
- Replace the ad‑hoc, env‑gated direct‑write path with a typed capability (`DirectWritableSink`) negotiated in `pump_ranges` without concrete type checks.
- Keep `MemoryManager` as a single public façade, but streamline its internals with clear CPU/GPU pods and add a single explicit `finalize_load()` hook so we can remove `UnifiedMemorySink` from the hot path.

Additionally, we remove stringly‑typed DVMP lookups in sinks by passing a per‑model `DvmpRegion` handle, and make UMA a read‑through for CPU chunk state (DVMP is authoritative), preserving UMA as SoT for GPU. A complete list of deprecations and replacements appears in Section 11.

Collectively, these changes strike a simpler balance: fewer abstractions in the hot path, clearer ownership lines, and faster remote→DVMP writes when supported — all without breaking public APIs.

## 1. What The Code Does Today (from code review)

Highlights from the current tree:
- DVMP (`core/common/memory/distributed_memory_pool.{h,cc}`)
  - Reserves contiguous CPU VA per model; tracks per‑chunk state; exposes `write_at`, `map_file_segments`, `lock/unlock`, and `pin_range` (pin leases protect exported/active ranges).
  - Provides a per‑model handle `DvmpRegion` that scopes calls under a per‑model lock, reducing global contention.
- Loader plumbing (`core/store/loader/*`)
  - Contracts: `Source`/`SeekableSource`, `Sink`/`PositionedSink`, `BufferPool` with `StreamingBufferAdapter`.
  - `pump()` and `pump_ranges()` implement staged copy via `StreamingPinnedBuffer`. `pump_ranges` includes an env‑gated direct path using `dynamic_cast<DVMPRegionSink*>` and a hardcoded `SCSTORE_ENABLE_DIRECT_DVMP=1`.
  - Sinks: `DVMPRegionSink` writes via DVMP `write_at`; `GPUMemorySink` does async H2D.
  - Sources: `FilePartitionSource` (disk), `RemoteKeySource` (RDMA/TCP) implements `supports_direct_write()` and `read_into()` using `DirectWriteToken`.
- Memory (`core/store/model/{memory_manager, model_memory_coordinator}.*`)
  - `MemoryManager` is a façade for DVMP/UMA/comm/transfer and streaming buffers. It already plans direct writes by issuing DVMP pin leases and building a `DirectWriteToken`.
  - UMA maintains chunk state for both CPU and GPU; for CPU it often mirrors DVMP metadata, creating duplication risk.
- Model (`core/store/model/model.{h,cc}`)
  - Orchestrates allocation and dispatch to loaders/copies. Public API is stable and clean.

Issues surfaced in code:
- Direct path is coupled to a concrete sink via `dynamic_cast` plus an env flag; capability should be negotiated by interfaces, not types or env.
- `DVMPRegionSink` forwards `model_id` to DVMP for each call; a lightweight `DvmpRegion` is already available and avoids global lookups.
- UMA duplicates CPU state updates that DVMP already manages; a read‑through view would be simpler and safer.
- `UnifiedMemorySink` adds an abstraction whose primary job is post‑write state updates; it can be replaced by a single `MemoryManager::finalize_load()` helper, simplifying the loader pipeline.

Additional notes from tracing flows in code:
- DVMP already exposes a per‑model lock via `DvmpRegion`; leveraging it avoids global map contention during `write_at`/`lock_chunks` bursts.
- `MemoryManager::plan_direct_write` already builds `DirectWriteToken` with lease keepalives; the capability interface becomes a thin forwarder.
- `RemoteKeySource` already implements `supports_direct_write()` and `read_into()` with RDMA; negotiation is straightforward.

## 2. Goals and Design Principles

- Reduce conceptual count in hot paths; remove unnecessary abstractions.
- Make ownership explicit and layered: DVMP owns CPU VA policy and metadata; UMA owns GPU chunk state; loaders stream through a minimal API.
- Prefer small, additive interface changes over churn; keep public Model/MemoryManager APIs stable.
- Enforce correctness by design (positioned writes only) with clear back‑pressure.
- Keep error handling local to the layer that owns the policy/resource (DVMP for CPU VA, MemoryManager for state transitions, loader for IO orchestration).

## 3. Design

### 3.1 Single Sink Contract

- Standardize on `PositionedSink` for all loader data paths. Positioning eliminates reordering bugs under concurrency and removes branches.
- Treat `pump()` as a thin wrapper that delegates to `pump_ranges()` with `[0, total_bytes)`; remove the separate sequential consumer path.
- Keep `close()` on `PositionedSink` for lifecycle symmetry.

Impact
- `UnifiedMemorySink::write()` and any paths that rely on non‑positioned writes are phased out; tests migrate to positioned writes.
- The `pump()` helper becomes a trivial wrapper around `pump_ranges()` and loses its separate sequential consumer branch.

### 3.2 Capability‑Driven Direct Writes (no env, no concrete type checks)

- Add a tiny capability interface implemented by sinks that can plan direct writes into their destination VA:

  ```cpp
  // loader/sink.h
  class DirectWritableSink {
   public:
    virtual ~DirectWritableSink() = default;
    virtual absl::StatusOr<stepcast::store::DirectWriteToken> plan_direct_write(
        absl::Span<const stepcast::store::VaRange> ranges) = 0;
  };
  ```

- Update `pump_ranges` to negotiate directly when `SeekableSource::supports_direct_write()` and `dst` implements `DirectWritableSink`; remove the env‑gated, DVMP‑specific branch. Fallback to staged pump on negotiation failure.
- Implement `DirectWritableSink` in DVMP sinks by delegating to `MemoryManager::plan_direct_write()`; the token already carries DVMP pin‑lease keepalives.

Benefits
- Interface‑driven, extensible, and testable. No type casts or env flags in core pumping logic.
- Clear error surfaces: if token planning fails (e.g., pin lease denied), `pump_ranges` falls back to staged path automatically.

### 3.3 DVMP Per‑Model Handle in Sinks

- Change `DVMPRegionSink` to hold `memory::DistributedVirtualMemoryPool::DvmpRegion` instead of a `MemoryManager` pointer. Construction receives `{region, total_size}` and `write_at()` simply delegates to `region.write_at(offset, src, bytes)`.
- `MemoryManager` exposes a getter for `DvmpRegion` after allocation.

Benefits
- Eliminates string lookups (`model_id`) at each write and narrows coupling; per‑model locking stays effective.
- Creates a self‑documenting construction contract for sinks (region + size), reducing accidental misuse.

### 3.4 UMA Read‑Through for CPU; UMA Owns GPU

- UMA drops mutation of CPU chunk state; it reads CPU state via `dvmp->chunk_snapshot()` when needed for scheduling/inspection.
- UMA remains the sole owner of GPU chunk state and device‑specific counters.
- Post‑load updates for GPU (and optional chunk subsets) are performed via a new `MemoryManager::finalize_load()` helper (Section 3.5).

Benefits
- Single source of truth for CPU metadata (DVMP) and GPU metadata (UMA); less drift and simpler reasoning.
- UMA’s CPU logic simplifies to a periodic sync or on‑demand read from DVMP’s snapshot.

### 3.5 Lean MemoryManager Internals + Explicit Finalization Hook

- Keep the public façade; internally split state into two tiny pods guarded by separate mutexes:
  - CPU: `{ MemoryState, base, bytes, StreamingPinnedBuffer, comm_registered, CommRegistrationInfo }`
  - GPU: `{ MemoryState, CudaMemory, stream, stream_ready, comm_registered, CommRegistrationInfo }`
  - Add a single explicit helper invoked by loaders after successful `sink.close()`:
  - `absl::Status finalize_load(ModelLocation target, std::optional<absl::Span<const uint32_t>> chunks)`
  - Applies UMA updates for GPU (full or partial); CPU metadata is already updated by DVMP `write_at()`.
  - Remove `UnifiedMemorySink` from the pipeline; loaders call `finalize_load()` explicitly.
  - Keep `plan_direct_write()` and `chunk_snapshot()` as they are; both are already correct and efficient.

Implementation notes (MM refactor steps):
- Step A: Extract internal helpers from `copy_data_async` into: `capture_copy_context_`, `launch_copy_task_`, and `finalize_copy_state_` (no behavioral change).
- Step B: Introduce private structs `CpuPod` and `GpuPod` to group related fields; migrate methods to use pods; keep existing public API intact.
- Step C: Ensure `finalize_load()` is the only place that updates UMA post‑load; `finalize_load_state()` remains responsible only for `MemoryState` transitions.
- Step D: Reduce direct DVMP calls to region-oriented helpers; keep `get_dvmp_region()` public and cache base address for fast paths.

Benefits
- Fewer runtime objects, less indirection; clearer locking; simpler tests.
- Explicit finalization point prevents accidental “forgotten state update” bugs and removes the need for `UnifiedMemorySink`.

### 3.6 Alignment and Chunking Policy Enforcement

- Enforce alignment once inside `ensure_streaming_buffer(...)`: ensure pool chunk size is a divisor of DVMP chunk and O_DIRECT‑friendly. Fail fast with `InvalidArgument` otherwise.
- Keep current chunk sizing defaults (8–16 MiB) unless workload dictates a different sweet spot.

Rationale: This consolidates all alignment policy in one place (MemoryManager), rather than distributing checks across loaders and pools.

### 3.7 Optional: Disk→DVMP Mappings (deferred)

- Keep `map_file_segments` as a DVMP capability but don’t add a “mmap sink” yet. It can be introduced later behind a guard if benchmarks justify it for very large models.

Safety note: writable mappings require careful remap semantics; the current `write_at` approach remains the safer default.

## 4. API Deltas (minimal and additive)

Public additions (backward compatible):
- `loader/sink.h`: `class DirectWritableSink` (new).
  - `MemoryManager`:
    - `absl::Status finalize_load(ModelLocation, std::optional<absl::Span<const uint32_t>>)` (new).
    - `absl::StatusOr<memory::DistributedVirtualMemoryPool::DvmpRegion> get_dvmp_region() const;` (new).
    - `absl::Status finalize_load_state(ModelLocation, const absl::Status&)` (clarified to state transitions only; UMA update moves to `finalize_load`).

Behavioral changes:
- `pump_ranges(...)` prefers capability‑driven direct writes; removes the env‑gated DVMP‑specific branch.
- Loader code constructs `DVMPRegionSink` with a `DvmpRegion` and calls `memory_manager.finalize_load(...)` after `close()`.
- `UnifiedMemorySink` is removed from the hot path (eventually deleted after migration).

Non‑functional clarifications:
+ `pump()` has been removed. Use `pump_ranges()` with explicit ranges (single‑range `[0, total_bytes)` for whole‑model loads).

Non‑goals (unchanged public surface):
- `Model` public API; `IModelLoader` signatures; `MemoryManager` existing public methods.

## 5. Migration Plan

Phase 1 — Interfaces and negotiation (low risk)
1) Add `DirectWritableSink` and implement it in `DVMPRegionSink` via `MemoryManager::plan_direct_write`.
2) Update `pump_ranges` to use capability negotiation; keep the old env‑gated code behind a compile‑time flag for one release if desired.

Phase 2 — DVMP region handle
3) Add `MemoryManager::get_dvmp_region()` and change `DVMPRegionSink` ctor to accept a `DvmpRegion`. Update Disk/P2P loaders accordingly.

Phase 3 — Lean MM internals and explicit finalize
4) Add `MemoryManager::finalize_load()`; migrate loader sites to drop `UnifiedMemorySink` and call `finalize_load()` after `sink.close()`.
5) Internally refactor `MemoryManager` into CPU/GPU pods (private) with small helpers for copy capture/finalize. No public signature changes.
   - A1: Split `copy_data_async` into capture/launch/finalize helpers.
   - A2: Introduce `CpuPod`/`GpuPod`; mechanical field move only.
   - A3: Add DVMP region accessor usage at call sites to avoid string lookups.

Phase 4 — UMA CPU read‑through
6) Remove CPU state mutation from UMA; serve CPU chunk views via DVMP snapshot. Keep GPU state mutation in UMA.

Phase 5 — Cleanup
7) Remove `UnifiedMemorySink` and the deprecated env‑gated branch in `pump_ranges` after one release cycle.

## 6. Performance, Maintainability, and Trade‑offs

- Performance
  - Direct write on by default when supported saves an extra copy and system calls vs staged path; removes a branch and a `dynamic_cast` in a hot loop.
  - Using `DvmpRegion` avoids repeated map lookups and reduces locking contention further (per‑model lock only).
  - Enforced alignment reduces short reads/writes for disk paths.
- Maintainability
  - Fewer concepts in the loader pipeline (no `UnifiedMemorySink`), smaller and clearer `pump_ranges`.
  - UMA boundaries are cleaner (CPU view, GPU owner), reducing duplication and drift risk.
  - `MemoryManager` continues to be the single façade but is easier to test via small internal helpers and an explicit finalization call.
- Trade‑offs
  - Call sites become slightly more explicit (call `finalize_load()`), but the total abstraction count goes down and responsibilities are clearer.
  - Some temporary duplication during the migration window (old env branch retained behind a flag) to ensure safe rollout.

Expected performance deltas (targets):
- Remote→CPU (RDMA) direct write path: 5–15% wall‑time improvement vs staged copies for 10–50 GB models, depending on NIC and NUMA topology.
- Disk→CPU and CPU→GPU remain at parity; minor improvements from reduced contention (per‑model DVMP handle) and cleaned pump.

## 7. Risks and Mitigations

- Misuse of `DirectWriteToken` outside sinks: only sinks produce tokens; tokens carry DVMP pin‑lease keepalives bound to the model/VA ranges.
- Partial loader migrations: keep the old branch behind a build flag for one release, then remove.
- UMA logic changes: gate UMA CPU mutation removal behind unit tests that assert equivalence with DVMP snapshots for representative paths.

Concurrency pitfalls considered:
- DVMP per‑model lock ensures correctness for `write_at` and transitions across multiple producers.
- MemoryManager’s explicit finalize avoids dangling intermediate states in case of partial failures.

- Optional DVMP mapping sink for disk remains out of scope here; consider introducing when measurable benefits exist.
- Token format may be extended for non‑RDMA engines (shared memory, alternative NICs) without changing the negotiation interface.

## 10. Sketches and Concrete Call‑Site Changes

DVMP sink capability:
```cpp
class DVMPRegionSink : public PositionedSink, public DirectWritableSink {
 public:
  struct Options { memory::DistributedVirtualMemoryPool::DvmpRegion region; uint64_t total_size = 0; };
  explicit DVMPRegionSink(Options opts);
  absl::Status write_at(uint64_t off, const void* src, size_t bytes) override {
    if (off + bytes > opts_.total_size) return absl::OutOfRangeError("overflow");
    return opts_.region.write_at(off, src, bytes);
  }
  absl::StatusOr<DirectWriteToken> plan_direct_write(absl::Span<const std::pair<uint64_t,size_t>> ranges) override {
    return mm_->plan_direct_write(/* convert to VaRange */ ...);
  }
 private:
  Options opts_;
};
```

Pump negotiation (no env/type checks):
```cpp
if (auto* cap = dynamic_cast<DirectWritableSink*>(&dst); cap && src.supports_direct_write()) {
  ASSIGN_OR_RETURN(auto token, cap->plan_direct_write(ranges));
  for (auto [off,len] : ranges) ASSIGN_OR_RETURN(auto got, src.read_into(off, len, token));
  return dst.close();
}
// else staged path
```

Loader close‑out (no UnifiedMemorySink):
```cpp
ABSL_CHECK_OK(sink->close());
ABSL_CHECK_OK(mem_manager->finalize_load(target_location, /*optional chunk list*/));
```

## 11. Deprecated Modules and EOL Plan

This section enumerates all modules and code paths deprecated by this RFC (and one historical removal for completeness), with replacements and removal timelines.

- `core/store/loader/unified_memory_sink.{h,cc}`
  - Status: Deprecated (to be removed after one release cycle)
  - Rationale: Exists only to update chunk states around writes; replaced by explicit `MemoryManager::finalize_load()` call.
  - Replacement: Call `sink->close()` then `memory_manager->finalize_load(target_location, optional_chunk_list)`.

- `pump.cc` env‑gated direct write branch using `SCSTORE_ENABLE_DIRECT_DVMP` and `dynamic_cast<DVMPRegionSink*>`
  - Status: Deprecated (remove after one release cycle)
  - Rationale: Type‑based and env‑gated; replaced by capability negotiation.
  - Replacement: `DirectWritableSink` capability in `sink.h`; negotiation in `pump_ranges`.

- `core/store/loader/dvmp_region_sink.{h,cc}` options that accept `MemoryManager` and forward string `model_id` to DVMP
  - Status: Deprecated (replace in next release)
  - Rationale: Avoids repeated global lookups and string plumbing; make scoping explicit.
  - Replacement: Accept `memory::DistributedVirtualMemoryPool::DvmpRegion` in `Options` and call `DvmpRegion::write_at`.

- `Sink::write()` usage in loader data paths and `RunConsumerSequential` in `pump.cc`
  - Status: Deprecated (retain interface for tests/ancillary uses; stop using in loader pipeline)
  - Rationale: Non‑positioned writes invite reordering bugs; all staged pumping should be positioned.
  + Replacement: Use `PositionedSink::write_at()`; call `pump_ranges()` with explicit ranges.

- UMA CPU state mutation APIs (e.g., `ModelMemoryCoordinator::update_chunk_states(... ModelLocation::PAGEABLE_CPU ...)`)
  - Status: Deprecated (becomes a no‑op and/or routes to DVMP snapshot)
  - Rationale: DVMP is authoritative for CPU chunk state.
  - Replacement: Read CPU state using `dvmp->chunk_snapshot()`; continue to mutate GPU state in UMA.

- Historical: legacy `dvmp_mapped_sink` and bespoke loader loops
  - Status: Already removed per RFC 0001; listed here to avoid confusion.
  - Replacement: `DVMPRegionSink` + (optional) `map_file_segments` for position‑controlled CPU IO.

Removal timeline and flags:
- Release N: introduce capability negotiation, `finalize_load()`, and `DvmpRegion` sinks; ship both paths behind `SCSTORE_ENABLE_LEGACY_PUMP=1` (default off).
- Release N+1: delete deprecated branches and remove `UnifiedMemorySink` from the tree.

## 13. Invariants and Error Semantics

- DVMP IO invariants
  - Only DVMP may perform `MAP_FIXED`/mprotect/remap into model CPU VA; sinks call `DvmpRegion::write_at()`.
  - Pin leases protect externally exported or directly written ranges until release.

- Loader invariants
  - All data paths use `PositionedSink::write_at()`. `pump()` is syntactic sugar over a single range.
  - Direct write is negotiated by capability; failures fall back to staged copies without partial writes.

- MemoryManager invariants
  - `finalize_load()` is called exactly once per loader operation; it must be idempotent.
  - CPU→GPU copy frees CPU pages per policy (tail eviction and buffer release) only after GPU reaches LOADED.

## 14. Observability and Metrics

- Preserve existing counters and add labels where useful:
  - DVMP: `dvmp_write_bytes_total`, `dvmp_map_bytes_total`, `dvmp_pin_leases_total{reason}`.
  - Loader: add `loader_bytes_total{source,location,mode}` where `mode ∈ {staged,direct}`.
  - Exposure: `chunk_exports_total{location}` remains.

## 15. Benchmark Plan (Representative)

- Data sets: 10 GB and 50 GB models (contiguous files and partitioned), large page‑aligned partitions.
- Scenarios:
  - Disk→CPU (staged), Remote(RDMA)→CPU (direct vs staged), CPU→GPU.
  - Mixed concurrent loads across multiple models to validate per‑model lock scaling.
- Platforms: PCIe Gen4 GPU, 100G RDMA NIC, modern NVMe.
- KPIs: throughput (GB/s), CPU utilization, time‑to‑ready, page faults, eviction churn.

## 16. Alignment with Engineering Rules

- Simplicity first: removes non‑essential abstractions from the hot path (UnifiedMemorySink) and favors single, explicit interfaces.
- Ownership clarity: DVMP owns CPU VA and metadata; UMA owns GPU; loaders orchestrate streaming only.
- Early returns and localized error handling: capability negotiation surfaces clear statuses; fallbacks are explicit and contained.
