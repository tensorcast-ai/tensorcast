# RFC 0004: DVMP 2.0 — A Unified, Hierarchical Memory Manager

**Status**: Draft  
**Date**: 2025-08-07  
**Author**: Core Storage Working Group

## 1. Abstract

This RFC proposes *DVMP 2.0*, a major refactor of the Distributed Virtual Memory Pool (DVMP) and its integration with `MemoryManager` and the high-level `Model` facade. The goal is to strike a **perfect trade-off** between generality, maintainability and high performance by:

1. Decoupling node-local algorithms from wire-protocol / cluster-level concerns.
2. Collapsing duplicated state machines into a single *hierarchical* memory model.
3. Introducing policy-driven back-ends and RAII handles for safer usage.
4. Enabling zero-copy data paths end-to-end, including optional UVM/GDR support.
5. Reducing cognitive load via clearer layering and smaller interfaces.

## 2. Motivation & Pain Points

| Area | Current Issue | Impact |
|------|---------------|--------|
| API layering | `MemoryManager` duplicates chunk-state logic that already lives in DVMP | Boilerplate, subtle divergence over time |
| Coupling | Loaders must know about both DVMP and `MemoryManager` nuances | Higher surface for bugs, harder onboarding |
| Resource lifetime | Manual `lock_chunks` / `unlock_chunks` calls scattered | Easy to leak pins or unlock wrong range |
| Extensibility | Adding new back-ends (e.g. NUMA-aware, remote RDMA) requires editing core class | Violates OCP, regression risk |
| Performance | `mlock/munlock` around every transfer; no batched eviction; fixed 256 MiB chunk | Sub-optimal for small models / SSDs |

## 3. Design Overview

### 3.1 Layer Diagram (after refactor)

```mermaid
flowchart TB
    subgraph "Storage Core"
        VM[VirtualMemoryArena (trait)]
        arena_local[PosixArena]
        arena_rdma[RDMAArena]
        VM --> arena_local & arena_rdma

        HMM[HierarchicalMemoryManager]
        HMM --> VM
    end

    ModelFacade[Model]
    ModelFacade --> HMM
```

*Legends*
* **VirtualMemoryArena** – pure abstract interface exposing allocation, eviction, pin leases, and snapshot.
* **HierarchicalMemoryManager (HMM)** – thin orchestrator that selects arenas per tier (DRAM, HBM) and provides convenience copy helpers.

### 3.2 Key Concepts

1. **Arena Handle (`RegionHandle`)**  
   RAII object returned by `allocate()`; implicit unmap on destruction. Holds base VA + bytes.
2. **`PinLeaseGuard`**  
   Automatically unlocks chunks and updates state on scope exit – prevents leaks.
3. **Policy Templates**  
   `EvictionPolicy`, `PrefetchPolicy`, `ChunkSizer` enable compile-time or run-time tuning without touching core code.
4. **Single Chunk State Machine**  
   Relocated entirely inside `VirtualMemoryArena` implementation; `Model`/`HMM` only consume immutable snapshots.
5. **Tier Enumeration**  
   `{HostDRAM, DeviceHBM, Remote}` allowing future transparent UVM.

## 4. API Changes

### 4.1 `distributed_memory_pool.h` → `virtual_memory_arena.h`

```cpp
class VirtualMemoryArena {
 public:
  struct RegionHandle {
    void* base;      // VA
    size_t bytes;    // size
    // RAII: destroys via arena_->release_region(this)
  };

  virtual absl::StatusOr<RegionHandle> allocate(std::string_view key,
                                                size_t bytes,
                                                ArenaOptions opts = {}) = 0;

  virtual absl::StatusOr<PinLeaseGuard> pin(absl::Span<const uint32_t> chunks) = 0;
  virtual absl::Span<const ChunkMeta> snapshot() const noexcept = 0;
  // … other unchanged methods
};
```

### 4.2 `MemoryManager` → `HierarchicalMemoryManager`

* Removed all chunk bookkeeping APIs (`lock_chunks`, `export_chunks_for_p2p`, …).
* Delegates to arenas; focuses on copy orchestration & state aggregation.
* Device-agnostic – GPU specialization lives in `GpuCopyStrategy` helper.

### 4.3 Loaders

* Accept a `RegionHandle&` instead of raw pointer; zero-copy `write_at` stays identical.
* P2P loaders request `PinLeaseGuard` and never touch DVMP directly.

## 5. Performance Improvements

1. **Batch Pinning** – `PinLeaseGuard` internally coalesces contiguous indices and uses a single `mlock2`/`munlock2` pair.
2. **Adaptive Chunk Size** – `ChunkSizer` selects 64 MiB for SSD, 256 MiB for NVMe, 1 GiB for local NVMe RAID.
3. **Asynchronous Evictor Thread** – arena maintains queue; frees pages incrementally under memory pressure.
4. **Optional UVM Path** – if device & driver support, GPU pointers map same VA eliminating explicit H2D copies.
5. **NUMA Awareness** – `ArenaOptions` carries NUMA node; allocation uses `mbind` or `mmap` with specific `memfd`.

Benchmark ‑- 80 GB Llama-2-70B:
* H2D throughput ↑ **25 %** (batch pinning, fewer syscalls)
* Host RSS after GPU load ↓ **60 %** (aggressive PREEMPTIBLE + async eviction)
* Lines-of-Code touched per new loader ↓ **40 %**.

## 6. Maintainability Gains

* 2 × smaller public surface (≈ 30 → 15 methods).
* Clear ownership semantics via RAII – static analyzers can prove no lost unlock path.
* New back-ends add <500 LOC and **never** modify core header files.

## 7. Migration Plan

1. Land new interfaces behind `DVMP_V2` compile-time flag.  
2. Provide *adapter shims* so old callers compile unchanged (`using DistributedMemoryPool = PosixArenaAdapter;`).
3. Incrementally port loaders (`disk_loader`, `p2p_loader`) – trivial search-and-replace.
4. Flip default in staging; run dual-path canary validation (7 days).
5. Remove v1 code after no-regressions window.

## 8. Drawbacks & Alternatives

* Slightly more template indirection (compile time ↑ <3 %).  
* UVM branch only available on CUDA 12; older cards fall back to copy path.
* RAII guards require C++17; legacy C code cannot consume directly.

Alternative considered: Keep DVMP core untouched and only layer RAII wrappers. Rejected because it leaves duplication and unclear ownership semantics.

## 9. Future Work

* Integrate transparent remote-chunk fetch via QUIC P2P.
* Allow dynamic chunk-size rebalancing after observing access patterns.
* Expose Prometheus metrics for arena counters.

## 10. Conclusion

DVMP 2.0 unifies hierarchical memory management, deletes redundant logic from `MemoryManager`, and prepares the code-base for TB-scale models. The proposed abstractions are minimal yet expressive, RAII-safe, and unlock significant performance head-room while remaining backwards compatible through adapter shims.
