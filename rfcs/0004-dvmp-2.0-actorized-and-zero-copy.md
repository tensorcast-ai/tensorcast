# RFC 0004 — DVMP 2.0: Actorized Per‑Model Handles, Correct GPU Copy Semantics, and Optional Zero‑Copy RDMA Into DVMP

Status: Proposed
Date: 2025‑08‑08
Owner: StepCast Core
Depends on: 0001 (DVMP), 0002 (Unified Loader Architecture), 0003 (DVMP‑Unified IO and Pin Leases)

## 0. Executive Summary

This RFC proposes DVMP 2.0 — an evolution of the Distributed Virtual Memory Pool and its integration with `Model` and `MemoryManager` to improve concurrency, correctness, and performance while keeping the codebase maintainable and testable.

Key changes:
- Actorize DVMP: introduce per‑model region handles with per‑model locks; the global lock is no longer a hot path.
- Make the GPU copy path chunk‑aware and state‑correct: ensure unified state transitions and DVMP unlocks on CPU→GPU copies even when not using loaders.
- Default to chunk‑scoped external exposure (pin leases + registration) and deprecate whole‑region CPU registration; keep a compatibility flag.
- Provide an optional zero‑copy P2P→DVMP path via a Source→Sink cooperative interface that writes directly into DVMP VA when safe; fall back transparently.
- Tighten DVMP I/O semantics (map vs. write) and clarify protection policies.
- Improve observability and fault isolation.

The design aims for a balanced trade‑off between generality (pluggable loaders, optional zero‑copy), maintainability (small API surface, clear responsibilities), and performance (reduced lock contention, fewer copies, correct pinning semantics).

## 1. Current State (Code Overview)

- DVMP core (`core/common/memory/distributed_memory_pool.{h,cc}`) provides VA reservation, per‑chunk metadata, `lock_chunks`/`unlock_chunks`, eviction/preemption, and DVMP‑owned I/O (`write_at`, `map_file_segments`) plus Pin Leases.
- Unified model memory (`core/store/model/unified_model_memory.{h,cc}`) tracks CPU/GPU chunk states, locks chunks for transfer, and updates states (GPU transitions call back into DVMP to unlock).
- Memory manager (`core/store/model/memory_manager.{h,cc}`) allocates DVMP region and GPU memory, stages copies through `StreamingPinnedBuffer`, registers memory for communication, and exposes unified operations.
- Loaders and pump (`core/store/loader/*`): `pump` and `pump_ranges` use BufferPool with positioned sinks; `DVMPRegionSink` writes via `dvmp->write_at`; `GPUMemorySink` performs async H2D copies; `MuxSeekableSource` implements P2P→disk fallback.

## 2. Gaps and Risks Identified

- Coarse locking in DVMP:
  - All operations take `DistributedMemoryPool::mutex_` covering `models_` and per‑model state. Under concurrent loads/exports, this can serialize unrelated models and increase tail latency.
- CPU→GPU copy path correctness and observability:
  - `MemoryManager::copy_data_async` performs a whole‑model staged copy but does not run UMA chunk transitions or DVMP chunk unlocks per chunk (only optional tail‐evict at the end). This prevents downstream from seeing `COPIED_GPU` per chunk and weakens tooling signals.
- External exposure safety defaults:
  - `enable_remote_memory_access(PAGEABLE_CPU)` registers the whole DVMP region by default. RFC 0003 introduced chunk‑scoped export via Pin Leases but the whole‑region path remains the default.
- Two CPU sinks remain:
  - `DVMPMappedSink` (mmap) still exists; `DVMPRegionSink` is the default via positioned writes. Having two fast paths complicates reasoning and testing; the mmap path also puts the kernel back in charge of paging when active.
- DVMP‑owned I/O protection policy:
  - `map_file_segments` maps with `PROT_READ`. When mixing mapped segments and later `write_at`, semantics can differ across kernels if callers expect read/write. The intended policy needs to be explicit.
- Limited zero‑copy from remote:
  - Current P2P path reads into a pinned staging buffer, then writes into DVMP. We can safely add a cooperative, optional direct‑to‑DVMP path under pin leases and registration.

## 3. Goals

- Reduce global contention and improve throughput under multi‑model and multi‑threaded loads.
- Make chunk state transitions consistent across loader‑based and `copy_data_async` paths.
- Make external exposure safe by default and explicit.
- Provide an optional zero‑copy remote→DVMP fast path with correctness guards.
- Keep APIs compact and narrow to preserve maintainability and testability.

## 4. Design

### 4.1 DVMP Actorization (Per‑Model Handles)

- Introduce a handle type `DvmpRegion` returned by `DistributedMemoryPool::open(model_id)`; on `allocate(model_id, bytes)` return both `VirtualRegion` and a `DvmpRegion` handle.
- Internally, refactor `models_` to store `std::shared_ptr<ModelInfo>` and move a per‑model `absl::Mutex` into `ModelInfo`. Global `mutex_` only protects the map.
- All operations (`write_at`, `map_file_segments`, `lock_chunks`, `unlock_chunks`, `mark_preemptible`, `pin_range`, `evict_tail_bytes`, `ensure_chunk_resident`, `refresh_chunks`) switch from global DVMP lock to the handle’s per‑model lock.
- Keep per‑chunk `ChunkMeta` atomics and `pin_refcnt` atomics (already present) — no additional fine‑grained locks needed.

API sketch (additions):
- `absl::StatusOr<DvmpRegion> open(std::string_view model_id) const;`
- `class DvmpRegion { public: /* same methods as DVMP but implicitly scoped to one model */ };`

Benefits:
- O(1) contention domain per model.
- Clearer lifecycle and easier testing (inject fake `DvmpRegion`).

### 4.2 Unified and Correct CPU→GPU Copy Semantics

- Add UMA‑backed chunk transitions to the `MemoryManager::copy_data_async` path to mirror loader behaviour, ensuring per‑chunk `LOCKED_TX → COPIED_GPU` and DVMP `unlock_chunks(..., copied_gpu=true)` occur.
- Implementation options (choose one):
  - A) Reuse the loader pipeline: internally construct a `SeekableSource` over DVMP VA, a `GPUMemorySink`, and a `UnifiedMemorySink`, then call `pump_ranges` over [0..N). Minimal new code, maximum consistency.
  - B) Keep the staging loop but surround each staged copy with UMA `lock_chunks_for_transfer` and `update_chunk_states` (per chunk or per batch) so DVMP unlocks are executed.

Either approach eliminates the current observability gap and aligns all transfers with the same state machine.

### 4.3 External Exposure: Chunk‑Scoped by Default

- Flip the default for CPU exposure to chunk‑scoped export using DVMP Pin Leases and contiguous VA groups. Whole‑region registration becomes an opt‑in compatibility flag (e.g., `scstore.enable_whole_region_cpu_export=false` by default).
- Consolidate the public API:
  - Keep: `export_chunks_for_p2p(...)`, `unexport_chunks_for_p2p(...)` in `MemoryManager` (already implemented).
  - Mark `enable_remote_memory_access(PAGEABLE_CPU)` as a compatibility shim; behind the scenes, implement it using a single VA range pin lease only when the flag is enabled.

### 4.4 Optional Zero‑Copy P2P→DVMP (Cooperative Fast Path)

- Add an optional cooperative interface allowing a `SeekableSource` to write directly into DVMP VA under a pin lease, bypassing the staging buffer:
  - New Source capability (probe‑able): `bool supports_direct_write() const;`
  - New method: `absl::StatusOr<size_t> read_into(uint64_t dest_va_offset, size_t bytes, DirectWriteToken token);`
  - `DirectWriteToken` is obtained from `MemoryManager` by: (1) coalescing chunk ranges, (2) acquiring DVMP pin leases, (3) registering those ranges with the communicator, and (4) providing the communicator’s registration descriptors keyed by VA offsets and sizes.
- In `pump_ranges`, when `dst` is `DVMPRegionSink` and `src.supports_direct_write()` is true, the consumer requests a `DirectWriteToken` for the destination range and calls `src.read_into(offset, ...)`; otherwise it falls back to the current staged path.
- Guardrails:
  - Require page alignment and min block sizes (e.g., ≥ 64 KiB).
  - Respect pin leases (no eviction/preemption for leased chunks).
  - Timeout and partial read semantics match existing `MuxSeekableSource` rules; partial completions fall back to staged reads automatically.

Net effect: direct RDMA/TCP → DVMP VA where safe, without broad API creep or maintenance burden; the fast path is opt‑in and fully optional at runtime.

### 4.5 DVMP I/O Policy and Protections

- Clarify and enforce the following rules:
  - Only DVMP issues `MAP_FIXED` mappings into model VA.
  - `map_file_segments` maps as `PROT_READ` by default (as today) and updates HOT/timestamps for the affected chunks.
  - `write_at` always targets anonymous (`PROT_READ|PROT_WRITE`) pages; if any VMA at the range is backed by a file, DVMP first remaps that subrange to anonymous via a private `mmap(MAP_FIXED|ANONYMOUS, PROT_READ|PROT_WRITE)` to avoid silent EFAULTs. DVMP handles sub‑chunk remapping precisely.
- Deprecate `DVMPMappedSink` from default flows; keep as a benchmark/diagnostic helper behind a build flag.

### 4.6 Observability and Fault Isolation

- Counters and gauges:
  - `dvmp_lock_acquire_total{op}` (lock_chunks, pin_range, write_at, map_file_segments, mark_preemptible, evict)
  - `dvmp_write_bytes_total`, `dvmp_map_bytes_total`, `dvmp_zero_copy_bytes_total`
  - `dvmp_pin_leases_total{reason}`, `dvmp_pinned_chunks`
- Timers:
  - `dvmp_write_at_latency_ms`, per‑model
  - `copy_cpu_to_gpu_batch_ms`, `read_into_direct_ms`
- Error taxonomy for fast triage: all DVMP errors carry `{model_id, chunk_range}`; surface via logs and metrics.

## 5. API Changes (Summary)

- DVMP:
  - Add `open(model_id) -> DvmpRegion` handle; migrate methods to handle (keeping legacy methods as thin wrappers for one release).
  - Strengthen `write_at`: ensure writable VMA semantics even after file mappings.
- MemoryManager:
  - Add a consolidated helper to obtain `DirectWriteToken` for a set of VA ranges (internally performs pin leases + communicator registration).
  - Update `copy_data_async` to use UMA chunk transitions and DVMP unlocks (either via pump reuse or explicit lock/update calls).
  - Flip default to chunk‑scoped export; gate whole‑region registration behind a flag.
- Loader/Pump:
  - Extend `SeekableSource` with optional `supports_direct_write()` and `read_into(...)`.
  - In `pump_ranges`, detect and use the cooperative fast path when available.

## 6. Migration & Rollout Plan

1) DVMP internals (safe, behaviour‑preserving)
- Refactor `models_` to `shared_ptr<ModelInfo>` with per‑model mutex; wrap public methods to lock per‑model.
- Add legacy wrappers to maintain the current class surface during migration.

2) Correct CPU→GPU semantics
- Implement either A) pump reuse in `copy_data_async` or B) UMA per‑chunk transitions around the staged loop. Add tests to verify per‑chunk `COPIED_GPU` and DVMP unlocks.

3) Default chunk‑scoped export
- Add config flag `scstore.enable_whole_region_cpu_export` (default false). Switch `enable_remote_memory_access(PAGEABLE_CPU)` to chunk‑scoped or conditional shim.

4) Optional zero‑copy P2P→DVMP
- Add `supports_direct_write()` and `read_into(...)` to `RemoteKeySource` and `MuxSeekableSource` (the latter simply forwards to its primary when possible, else falls back).
- Implement `DirectWriteToken` issuance in `MemoryManager` using DVMP pin leases and communicator registration.
- Guard with runtime feature flag `scstore.enable_zero_copy_p2p_to_dvmp` (default off).

5) Deprecate `DVMPMappedSink`
- Move out of default flow; keep behind `SCSTORE_ENABLE_DVMP_MMAP_SINK=1` for controlled benchmarking only.

6) Observability
- Add counters/gauges/timers; integrate with existing metrics registry.

## 7. Performance & Maintainability Impact

- Concurrency: per‑model locks reduce cross‑model contention; expected >2× improvement under concurrent loads of multiple models.
- CPU→GPU correctness: consistent UMA transitions unlock correct tail eviction and better pressure responses; improves stability and diagnosability.
- Optional zero‑copy: eliminates one DRAM copy per delivered byte on supported links, improving remote→CPU throughput by 1.1–1.4× depending on NIC and alignment.
- Maintainability: API surface grows modestly but cohesion improves (handles, explicit capabilities); removal of default mmap fast path simplifies mental model.

## 8. Testing Strategy

- Unit tests
  - DVMP: per‑model lock isolation, `write_at` over file‑mapped pages, pin leases reference counting, eviction skip for pinned.
  - UMA/MM: CPU→GPU staged copy transitions: `LOCKED_TX → COPIED_GPU` per chunk and DVMP unlocks observed.
  - Loader/Pump: direct‑write cooperation happy/partial/error cases; fallback correctness; range ordering preserved.
- Integration tests
  - Disk→CPU→GPU full load vs chunked load parity.
  - P2P→CPU with and without zero‑copy flag; mixed P2P→disk fallback.
- Stress
  - Multi‑model parallel loads (3–5 models) with eviction/preemption enabled.

## 9. Backward Compatibility

- Source, Sink, and Pump retain existing code paths; direct‑write is additive and opt‑in.
- Whole‑region CPU registration remains behind a flag for one release window; callers should migrate to chunk‑scoped APIs.
- DVMP legacy methods remain available; new handle‑based APIs preferred.

## 10. Open Questions

- Do we need a DVMP read path? Not now — reads are provided by sources. DVMP remains write‑only plus mapping control to avoid scope creep.
- How aggressive should `write_at` be in remapping over mapped file VMAs? Proposal: minimal necessary sub‑range remap with thorough metrics and warnings.
