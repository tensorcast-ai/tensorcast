## 2. 策略定义（做了什么）

### 2.1 Strategy A（`A_eager`）
核心思路：**先把 checkpoint 的全部 payload 顺序读入 GPU（payload buffer），再按照 plan 的 slice 把需要的内容 pack 到最终输出布局**。

阶段对应：
- `T(open_copy)`：磁盘 → pinned host → H2D，写入 GPU payload buffer（读取全 payload bytes）
- `T(pack)`：GPU 内 D2D “pack”（payload → output），把 plan 中的 slices 映射为最终紧凑输出布局

关键弱点（TP>1 且出现 `axis=1` 列切片时）：
- 列切片在 row-major 存储下会变成“每行一个小段”，若逐段 D2D memcpy，会产生 ~65 万次小拷贝调用（日志 `segments=656003`）。

本次优化（已实现）：
- 在 pack 阶段自动识别“等宽 + 固定 stride”的连续段序列，将其合并为 `cudaMemcpy2DAsync`（把 65 万级小 memcpy 调用降到少量 2D memcpy）。

### 2.2 Strategy B（`B_lazy_commit`）
核心思路：**不读全 payload；直接按 plan 展开出的 segments 从磁盘抓取需要的片段，并直接写入最终输出布局**（通过 VMM output buffer 做稀疏写入）。

优点：
- 理论上磁盘读取字节数接近 `bytes(output)`（不读无关数据）。

关键弱点（TP>1 且出现 `axis=1` 列切片时）：
- 列切片会展开成“每行一个小 segment”，导致 ~65 万次碎片化小读（`src_runs≈655k`，平均 25–50 KiB 一段），吞吐会被 IOPS/系统调用/调度开销打穿。

### 2.3 Strategy C（`C_batched_optimal`）
核心思路：在 B 的“全局已知计划/可批处理”的基础上，**把列切片（axis=1）从“65 万个小 segment”提升为“读连续 row-block → GPU staging → 2D pack”**，用少量额外读入字节换取连续 I/O。

两类路径：
- contiguous / 近似 contiguous slices：直接 disk→output（保持 B 的优势）
- `axis=1`（列切片，stride 模式）：disk→GPU staging（连续 row-block）→ `cudaMemcpy2DAsync` pack 到 output

对比 B 的关键变化：
- B 的瓶颈在“碎片化读”，C 将其变成“顺序读 + 少量 2D D2D pack”，显著提高磁盘→GPU有效带宽。

### 2.3b Strategy C_host_pack（对照：把 pack 放在 Host）

核心思路：沿用 C 的“按 checkpoint tensor 分组 + 顺序读 row-block”的决策，但把 pack 从 GPU copy engine 挪到 host：
- disk→host staging（连续 row-block）
- CPU 把每行 segment pack 到 pinned host buffer（只保留最终需要的列切片 bytes）
- 1D `cudaMemcpyAsync(H2D)` 一次性写入 output

预期收益与代价：
- 收益：H2D 只传 `bytes(output)`（而不是 row-block 的 `bytes(disk)`），对 TP=4 这类读放大场景尤其明显。
- 代价：CPU 侧 pack 变成额外的 DRAM→pinned memcpy（量级≈`bytes(output)`），在“source 很快（热 cache / DRAM / P2P）”的情况下，可能把瓶颈推到 CPU/DRAM/调度上。

### 2.4 Strategy D（预物化：materialize once, load many）
核心思路：对固定的 `loading-meta.json`（固定 TP 配置、固定切片/复制关系），第一次用 C 生成 output layout 后把结果落盘为每 rank 一个连续文件；后续加载直接顺序读 `bytes(output)`，避免 C 的 1.3–2.0× 读放大，也避免 B 的碎片化小读。

两阶段：
- **D/materialize**（一次性成本）：C（读 + pack） + GPU→host D2H + `pwrite(2)` 落盘（生成 `rankX.bin` + `rankX.meta.json`）。
- **D/load**（可重复）：从 `rankX.bin` 顺序读入 GPU（可用 `O_DIRECT` 测冷读上限）。

## 3. Plan 形态（为什么 TP>1 会难）

对三个 `loading-meta.json` 的扫描结论：
- `slices` 数组的最大长度：TP1=0，TP2=1，TP4=1（**没有多轴切片**）
- `axis` 只出现 0 和 1（**没有 axis>=2 的 N-D 切片**）
- slice 计数（按 slice 记录）：
  - TP2：axis0=1028，axis1=256
  - TP4：axis0=2056，axis1=512

解释：即使 axis=1 的条目数量不算多（256/512），它们通常对应**大 2D 权重**，展开后会产生海量“每行一个小段”的访问模式，直接决定 B 的崩溃和 A 的 pack 压力。

## 4. 基线：分解上限（磁盘→pinned host；pinned host→GPU；合并链路）

本节把端到端链路拆成两段，并给出两套**明确可复现**的上限参考：
- **热读（显式预热 page cache）**：先把模型 payload 完整读入内存（OS page cache），再对第二次读取计时。
- **冷读（O_DIRECT 绕过 page cache）**：用 `open(O_DIRECT)` + 对齐 `pread(2)` 直接读入 pinned host buffer。

### 4.0 热读上限（显式预热 page cache：先把模型读入内存）

说明：`safetensors_hot_*_baseline` 会先做一次**不计时 warmup**（顺序读完整 payload），再对第二次读取计时；因此结果不依赖“当前系统是否刚好命中 cache”。

1) **热读：磁盘(buffered)→pinned host**（不做 H2D）
- `--mode=safetensors_hot_host_baseline`（日志：`/tmp/tensorcast_safetensors_hot_host_baseline.log`）
  - payload bytes：61.027 GiB
  - 用时：5.607 s
  - 吞吐：**10.883 GiB/s**
  - 说明：该吞吐主要反映“page cache→userspace(pinned) copy + pump/调度开销”，不是 NVMe 冷读能力。

1b) **DRAM→pinned host（显式 DRAM mirror，用于与 page cache 热读互相印证）**
- `--mode=safetensors_dram_mirror_host_baseline`（日志：`/tmp/tensorcast_safetensors_dram_mirror_host_baseline.log`）
  - measured bytes：61.027 GiB
  - measured 用时：3.306 s
  - measured 吞吐：**18.462 GiB/s**
  - 说明：
    - 该模式会先把 payload 从 safetensors 读入一块用户态 DRAM（不计时），再测 DRAM→pinned host 的拷贝吞吐。
    - DRAM→pinned 明显高于 page cache→userspace（10.883 GiB/s），说明热读基线主要受 `pread(2)` 路径/内核 copy/系统调用与框架调度开销影响；而不是 CPU 内存带宽本身已经打满。
    - 更具体地讲，`safetensors_hot_host_baseline` 虽然“数据已在 DRAM（page cache）里”，但每个 chunk 仍然要走一次 `pread(2)`：VFS 层处理、file offset/页缓存查找、`copy_to_iter/copy_to_user` 的内核→用户拷贝（通常按页迭代）以及 syscall 边界的固定开销；这些都会把“纯 memcpy”能达到的吞吐拉下来。
    - `copy_to_user` 的“安全拷贝”路径通常也更难吃满带宽：要处理潜在 page fault、SMAP 的 uaccess 开关（`stac/clac`）、对象大小检查（`__check_object_size`）等；同时内核态拷贝通常不会走到用户态 `memcpy` 的最激进向量化/写合并实现（例如 AVX512 + non-temporal store 的组合）。
    - page cache 的底层是普通 page（常见为 4KiB）：对 61GiB 这种超大拷贝，会带来更高的 per-page 迭代与 TLB 压力；而 `dram_mirror_host_baseline` 的源 buffer 是匿名 `mmap`，在部分系统配置下可能以 THP（2MiB）承载，进一步降低 TLB 开销（因此更接近“理想 userspace memcpy”）。
    - NUMA 也会显著放大波动：page cache 页的物理放置由 warmup 时的线程/CPU 决定，而 pinned slab 的放置由 `--pinned_numa_node` 决定；两者若跨 socket，会把“page cache→pinned”的热读吞吐明显拉低（这也是为什么 H2D 并发测量中仅控 pinned NUMA 往往不够，还需要配合 CPU affinity）。
    - 另外，`dram_mirror_host_baseline` 测得的 18.462 GiB/s 也不是“机器 DRAM 带宽上限”，而是“本 benchmark 的 pump/buffer pool 框架 + memcpy”在当前线程数/NUMA/实现下的可达值；它更多用来衡量 **pread 热路径相对 userspace memcpy 的额外开销**。

2) **pinned host→GPU（纯 H2D）**（不读磁盘）
- `--mode=h2d_baseline`（日志：`/tmp/tensorcast_h2d_numa_tp1_default.log`）
  - bytes：8.000 GiB
  - 用时：0.157 s
  - 吞吐：**50.876 GiB/s**
  - 说明：该模式不走 `pump_ranges`，直接对每张 GPU 创建独立 stream，循环提交 `cudaMemcpyAsync(H2D)`；更接近“copy engine 峰值”，通常是一个偏乐观的上限。
  - PCIe 合理性校验（本机为 PCIe 5.0 x16）：
    - 实际链路：`nvidia-smi --query-gpu=index,pcie.link.gen.current,pcie.link.width.current --format=csv,noheader` 显示 4 张卡均为 `Gen5 x16`。
    - PCIe 5.0 速率：`32 GT/s/lane`，编码 `128b/130b`，单 lane 有效带宽约 `32 * 128/130 = 31.508 Gbit/s`。
    - x16 单向理论峰值约 `31.508 * 16 = 504.123 Gbit/s = 63.015 GB/s ≈ 58.7 GiB/s`（不含协议开销）。
    - 本次测得 `50.876 GiB/s ≈ 54.6 GB/s`，约为理论 `63.0 GB/s` 的 **~87%**，考虑 TLP/DLLP/事务开销与系统影响属于合理范围。

2b) **多 GPU 并发 H2D：吞吐随 GPU 数量的扩展性**

测试方式：同一进程内同时对多张 GPU 做 `pinned host → GPU` 拷贝（每张卡拷贝相同字节数 `bytes_per_gpu=8GiB`），最后以各 GPU 完成时间的最大值作为 makespan，输出聚合吞吐 `agg_GiB/s = (bytes_per_gpu * world_size) / makespan`。

（默认：不显式控制 pinned buffer 的 NUMA 放置）
- TP=1（日志：`/tmp/tensorcast_h2d_numa_tp1_default.log`）
  - `agg_GiB/s=50.876`（`gpu0=50.876 GiB/s`）
- TP=2（日志：`/tmp/tensorcast_h2d_numa_tp2_default.log`）
  - `agg_GiB/s=83.355`（`gpu0=41.678 GiB/s`，`gpu1=47.144 GiB/s`）
- TP=4（日志：`/tmp/tensorcast_h2d_numa_tp4_default.log`）
  - `agg_GiB/s=115.441`（`gpu0=28.971 GiB/s`，`gpu1=33.465 GiB/s`，`gpu2=28.860 GiB/s`，`gpu3=49.913 GiB/s`）

解读（为什么没有线性扩展到 `4 × 58.7 ≈ 234.8 GiB/s`）：
- 与理论值对比（以 `58.7 GiB/s * world_size` 为“PCIe 链路和”的粗上限）：TP=1 约 `86.6%`，TP=2 约 `71.0%`，TP=4 约 `49.1%`。
- **NUMA 拓扑导致不均衡**：`nvidia-smi topo -m` 显示 `GPU0/1/2` 的 CPU/NUMA affinity 为 `0`，`GPU3` 为 `1`；若 pinned host buffer 的物理页主要落在某个 NUMA node，则部分 GPU 会走跨 socket / UPI 路径，导致 per-GPU 吞吐显著不一致（TP=4 默认测得 `~29–50 GiB/s`）。

2c) **NUMA-aware pinned host：TP=4 并发 H2D 的上限可以更高**

实现：新增 benchmark flags `--pinned_numa_node` / `--pinned_numa_prefault`，在 `cudaHostRegister` 之前对 pinned host slab 做 best-effort NUMA 绑定并触页（避免 “pin 时隐式 fault” 导致的不可控放置）。

- TP=4，强制 pinned slab 绑定到 NUMA0（日志：`/tmp/tensorcast_h2d_numa_tp4_bind0.log`）
  - `agg_GiB/s=176.415`（`gpu0=45.434`，`gpu1=50.636`，`gpu2=45.433`，`gpu3=44.104`）
- TP=4，强制 pinned slab 绑定到 NUMA1（日志：`/tmp/tensorcast_h2d_numa_tp4_bind1.log`）
  - `agg_GiB/s=178.475`（`gpu0=45.977`，`gpu1=50.971`，`gpu2=45.976`，`gpu3=44.619`）
- TP=4，相比默认（115.441），**提升约 `1.53–1.55×`**；此时约为 “4×PCIe5x16 理论和” 的 `~75–76%`。
- 尝试 “每 GPU 一个 NUMA-local pinned pool”（日志：`/tmp/tensorcast_h2d_numa_tp4_per_gpu_auto.log`）并未带来改善（`agg_GiB/s=116.001`）；该现象需要进一步排查（可能与 IOMMU/VA 空间映射、访问模式或系统状态有关）。

结论：NUMA 对 “多 GPU 并发 H2D” 的影响可以非常大；在评估策略 A/B/C 的上限时，必须把 “pinned host buffer 的 NUMA 放置 + 线程/进程亲和性” 当作一级变量。

2d) **H2D 2D（模拟 `axis=1` 列切片）：`cudaMemcpy2DAsync(H2D)` 的有效带宽**

动机：用户提出“增大 pinned memory，让 pinned memory 能放下完整 tensor，然后用 `cudaMemcpy2DAsync` 一步到位写入 device 上的最终布局，去掉 pack”。为了回答“2D H2D 本身会不会比 1D H2D 慢”，新增了一个小基准：

- `--mode=h2d_2d_baseline`：用 `cudaMemcpy2DAsync(dst, dstPitch, src, srcPitch, widthBytes, height, cudaMemcpyHostToDevice, stream)` 测 **有效吞吐**  
  - `effective_bytes = widthBytes * height * iters`（注意：不包含 `srcPitch-widthBytes` 的 padding，因为 DMA 实际只搬运 widthBytes×height）
  - 典型 `axis=1` 形态：`srcPitch = full_cols * elem_bytes`，`widthBytes = slice_cols * elem_bytes`，`dstPitch = widthBytes`（packed output）

结果（TP=1，GPU0；`--h2d_bench_bytes=8GiB`）：
- 典型 dense（`[rows=5120, cols=5120]`，TP=4 slice_cols=1280，fp16）：`width=2560 srcPitch=10240 height=5120` → **50.310 GiB/s**（日志：`/tmp/tensorcast_h2d_2d_axis1_tp1_dense_w2560.log`）
- 典型 QKV（`[rows=5120, cols=15360]`，TP=4 slice_cols=3840，fp16）：`width=7680 srcPitch=30720 height=5120` → **51.076 GiB/s**（日志：`/tmp/tensorcast_h2d_2d_axis1_tp1_qkv_w7680.log`）
- 典型 MLP gate/up（`[rows=5120, cols=27648]`，TP=4 slice_cols=6912，fp16）：`width=13824 srcPitch=55296 height=5120` → **50.970 GiB/s**（日志：`/tmp/tensorcast_h2d_2d_axis1_tp1_default.log`）
  - 对照（很窄的 width 会掉速；`--h2d_bench_bytes=2GiB`）：
    - `width=256 srcPitch=10240 height=5120` → **29.703 GiB/s**（日志：`/tmp/tensorcast_h2d_2d_axis1_tp1_w256.log`）
    - `width=512 srcPitch=10240 height=5120` → **33.535 GiB/s**（日志：`/tmp/tensorcast_h2d_2d_axis1_tp1_w512.log`）

解读：
- 在这些“真实模型常见的 axis=1 slice 宽度（2.5–13.5KiB/row）”下，`cudaMemcpy2DAsync(H2D)` 的有效带宽与 `cudaMemcpyAsync(H2D)` 基本一致（≈50–51 GiB/s），因此 **“2D H2D”本身不是性能短板**。
- 但你的担心在 “width 很小” 时确实成立：`cudaMemcpy2DAsync(H2D)` 内部即使只提交一次 API，也需要在 DMA 侧处理 `height` 行的地址步进与映射/描述符；当 `widthBytes` 小到不足以摊平 per-row 开销时，有效带宽会明显低于 1D 大块 H2D。
- 但这并不等价于“端到端会大幅变快”：在本报告的 TP=4 Strategy C 中，`T(pack)` 已经只有 **0.022s/5.990s（<0.4%）**，即使彻底去掉 pack，理论收益也非常有限；要显著缩短 makespan 仍然需要优先从“减少总读量/减少碎片化/更强 overlap”入手。

3) **热读端到端：磁盘(buffered)→pinned host→GPU（合并链路，包含 H2D）**
- `--mode=safetensors_hot_disk_baseline`（日志：`/tmp/tensorcast_safetensors_hot_disk_baseline.log`）
  - payload bytes：61.027 GiB
  - 用时：5.594 s
  - 吞吐：**10.910 GiB/s**

解读：
- 热读场景下，`H2D` 上限远高于端到端吞吐，因此瓶颈主要在 **host 侧（page cache→用户态 copy + pump/调度）**，而不是 PCIe/H2D。
- `hot_host_baseline (10.883)` 与 `hot_disk_baseline (10.910)` 接近，说明“加入 H2D”并没有成为瓶颈（符合 H2D≈50 GiB/s 的测量）。
- `dram_mirror_host_baseline (18.462)` 可以视为“去掉系统调用/内核 copy 后”的用户态上限参考；它与 `hot_host_baseline` 的差距就是 page cache 热读路径的额外开销量级。

### 4.1 冷读上限（绕过 page cache）

为得到冷读上限，新增了 `O_DIRECT` 基线（绕过 OS page cache；日志里会显示 `skipped_tail_bytes`，表示每个文件末尾不足 512B 的 tail 被跳过，对总量影响可忽略）：

1) **冷读：磁盘 O_DIRECT→pinned host（不做 H2D）**
- `--mode=safetensors_o_direct_host_baseline`（日志：`/tmp/tensorcast_safetensors_o_direct_host_baseline.log`）
  - bytes：61.027 GiB（按 512B 对齐后的总和；包含极小的 header/对齐差异）
  - 用时：10.854 s
  - 吞吐：**5.623 GiB/s**

2) **冷读端到端：磁盘 O_DIRECT→pinned host→GPU（包含 H2D）**
- `--mode=safetensors_o_direct_disk_baseline`（日志：`/tmp/tensorcast_safetensors_o_direct_disk_baseline.log`）
  - bytes：61.027 GiB（对齐后）
  - 用时：10.204 s
  - 吞吐：**5.981 GiB/s**

结论：在冷读条件下，磁盘端吞吐约 **5.6–6.0 GiB/s**；H2D 仍远高于磁盘，因此冷读上限依然是磁盘主导。

### 4.2 如何用拆分基线估计“理论下限时间”

对任意一次加载（或某个阶段）可用两个上限做一个很粗的下界：
- `T_min_disk_to_host ≈ bytes(disk) / BW(disk→pinned)`
- `T_min_h2d ≈ bytes(h2d) / BW(H2D)`
- `T_min_io ≈ max(T_min_disk_to_host, T_min_h2d)`（两段不能比瓶颈更快；实际可能通过 overlap 接近这个下界，但不会小于它）

代入本次测得的上限（两套）：
- 热读：`BW(disk→pinned) ≈ 10.883 GiB/s`（显式预热 page cache）
- 冷读：`BW(disk→pinned) ≈ 5.623 GiB/s`（O_DIRECT）
- `BW(H2D) ≈ 50.876 GiB/s`（pinned host→GPU，单卡）

对本报告中“未显式控制冷/热”的 loader runs，建议把下界当作一个区间：
- `T_min_hot ≈ bytes(disk) / 10.883`（热读下界）
- `T_min_cold ≈ bytes(disk) / 5.623`（冷读下界）

补充：如果你只关心“端到端冷读（磁盘→GPU）”的上限，也可以直接用 `BW_cold_disk2gpu ≈ 5.981 GiB/s`（`safetensors_o_direct_disk_baseline`）。

### 4.3 基线模式的 copy 行为拆解（系统调用/原语级）

这里用最常用的链路（`safetensors_disk_baseline` / Strategy A 的 `T(open_copy)`）作为例子，把“传输过程”拆成可对应到 OS/CUDA 原语的步骤：

1) **分配并固定 host bounce buffer（pinned）**
- `aligned_alloc(4096)`：分配一块对齐的用户态内存（便于 O_DIRECT 对齐、也便于页级管理）。
- `cudaHostRegister(ptr, bytes, cudaHostRegisterDefault)`：把这块 host 内存注册为 pinned（可被 GPU DMA 直接读取）。

2) **磁盘 → pinned host**
- `open(2)`：逐个打开 `.safetensors` 分片文件（默认 buffered I/O）。
- `pread(2)`：把 payload bytes 读入 pinned host bounce buffer。
  - buffered I/O 情况下，内核可能从 page cache 拷贝到用户 buffer；若未命中 cache，则会触发块层读请求后再拷贝到用户 buffer。
- 冷读基线（`safetensors_o_direct_*`）使用 `open(2)` + `O_DIRECT`，并要求 offset/len/buffer 都按 512B 对齐，然后用 `pread(2)` 直接把数据读入用户 buffer（绕过 OS page cache）。

3) **pinned host → GPU**
- 由 `AsyncCopyManager::submit_h2d(...)` 提交 H2D：核心原语等价于 `cudaMemcpyAsync(dst_dev, src_host, bytes, cudaMemcpyHostToDevice, stream)`（底层 driver API 为 `cuMemcpyHtoDAsync`）。
- completion 通常通过 CUDA event / `cudaStreamSynchronize` 来等待（benchmark 的 `h2d_baseline` 用 event query + makespan 统计；`GpuMemorySink` 的同步写路径会对 handle `wait()`，pump 路径尽量避免 per-chunk 等待以实现 overlap）。

4) **GPU pack（仅 A/C 才有，属于“GPU 内拷贝”而非 IO）**
- 原语一般是 `cudaMemcpyAsync`（D2D）或 `cudaMemcpy2DAsync`（当切片呈现“固定 stride + 等宽”的 2D 模式时）。

这 4 类动作覆盖了“磁盘→host→GPU”路径中最主要的 copy 行为；因此在做“上限/瓶颈”分析时，通常就是分别看：`pread(2)`（是否碎片化、是否 O_DIRECT）与 `cudaMemcpyAsync`（是否能吃满 PCIe/host 内存带宽）。

## 6. 瓶颈与上限差距分析（按策略/阶段）

为便于对比，下文用：
- `BW_disk2gpu ≈ bytes(disk)/T(IO阶段)`（GiB/s）
- `BW_d2d ≈ bytes(d2d)/T(pack)`（GiB/s）

并用两套上限估算“可能达到的最低 IO 时间”（下界）：
- 热读（显式预热 page cache 的端到端）：`BW_hot_disk2gpu ≈ 10.910 GiB/s`
- 冷读（O_DIRECT 端到端）：`BW_cold_disk2gpu ≈ 5.981 GiB/s`
对应下界区间：`T_min_io ∈ [bytes(disk)/10.910, bytes(disk)/5.981]`。

### 6.1 Strategy A：**IO 绑定（读全 payload）**，pack 已接近最优

#### A 的硬件瓶颈
- **主瓶颈：NVMe→CPU→GPU 的读链路带宽**（磁盘吞吐、DMA、CPU 参与的拷贝/调度、H2D copy engine 等共同决定）
- GPU HBM 带宽不是主要瓶颈（优化后 pack 极快）

#### 关键数据点
- TP=1：`T(open_copy)=7.350s`，61.027GiB → **8.303 GiB/s**（低于热读上限 10.910，且显著快于冷读上限 5.981，说明该次 run 更接近“热/混合读”）
- TP=4（优化后）：`T(pack)=0.022s`，15.257GiB → **680 GiB/s**（pack 基本已接近“设备内 memcpy”可达范围）

#### A 离上限有多远？
以 TP=4 rank0（优化后）为例：
- A 的理论最低 IO 时间（读全 payload）：
  - 热读下界：`61.027/10.910 = 5.593s`
  - 冷读下界：`61.027/5.981 = 10.204s`
- 实测 `T(open_copy)=10.123s`（接近冷读下界；这类波动通常来自 page cache 状态、并发系统负载、NUMA 路径等）

结论：
- **A 的 pack 阶段已接近最优**（不再是瓶颈）。
- **A 的端到端上限受“必须读全 payload”约束**：即使完全吃满热读上限（~10.9 GiB/s），在 TP>1 时也很难在端到端上追上“少读字节”的 C。

### 6.2 Strategy B：TP>1 时被“碎片化读 + IOPS/系统调用”完全压垮

#### B 的硬件瓶颈
- **主瓶颈：碎片化小读导致的 IOPS/调度/系统调用开销**（远早于磁盘带宽上限）
- 这类瓶颈表现为：`bytes(disk)` 不大，但 `T(commit)` 极长，`src_runs≈655k`，平均每段 25–50 KiB

#### 关键数据点（TP=4 rank0）
- `bytes(disk)=15.257GiB`
- `T(commit)=46.720s` → `BW_disk2gpu ≈ 0.327 GiB/s`
- 以上限估算下界区间：
  - 热读下界：`T_min_hot = 15.257/10.910 = 1.398s`
  - 冷读下界：`T_min_cold = 15.257/5.981 = 2.551s`
- 实测相当于 **~25× 慢于“顺序读上限”**

#### 额外验证：热 cache 也救不了 B（Qwen2.5-32B 的 axis=1 形态本质太碎）

为了排除“只是碰巧没命中 page cache”的疑问，我们先用 `safetensors_hot_host_baseline` 显式把全量 payload 预热进 page cache，再跑 B：
- 日志：`/tmp/tensorcast_vllm_tp4_b_rank0_hotcache.log`
  - `T(commit)=45.274s`（几乎与未预热时一致）

同时用 `disk_fragmentation` 构造一个“近似 axis=1 切片”的 strided 访问模式（TP=4 的 axis=1 col_size 取 6912 元素，fp16 → `seg_bytes=6912*2=13824`，row_bytes≈`27648*2=55296` 作为 stride）：
- 冷读（O_DIRECT）：`/tmp/tensorcast_disk_fragmentation_axis1_like_direct_ok.log` → **0.197 GiB/s**
- buffered：`/tmp/tensorcast_disk_fragmentation_axis1_like_buffered_ok.log` → **0.178 GiB/s**

结论：在这台机器 + 这组权重布局上，“读更少字节但访问形态碎”会把吞吐压到 <0.3 GiB/s 量级；因此 B 想接近带宽上限，必须像 C 那样改变读形态（顺序读超集 + pack），而不是单纯依赖 page cache 或调参。

结论：
- **B 的瓶颈不是带宽，而是碎片化访问形态本身**；在当前 checkpoint layout + axis=1 切片组合下，B 远未达到最优。
- 若不改变“读形态”（例如引入 staging/批处理/合并读），单纯调参（增大 bbuf、改 io_threads）通常无法把 25× 的差距补回来。

### 6.3 Strategy C：IO 接近上限 + pack 接近最优，但仍有 1.3–1.6× 头部空间

#### C 的硬件瓶颈
TP>1 时，C 的主瓶颈回到 **“顺序/大块 IO 链路带宽”**（这是正确的方向）：把 B 的 IOPS 瓶颈转换为带宽瓶颈。

#### 关键数据点
- TP=4 makespan=rank1：
  - `bytes(disk)=30.263GiB`
  - `T(commit)=3.395s` → `BW_disk2gpu ≈ 8.913 GiB/s`（低于热读上限 10.910，显著高于冷读上限 5.981）
  - `bytes(d2d)=5.000GiB`，`T(pack)=0.008s` → `BW_d2d ≈ 591 GiB/s`

#### C 离上限有多远？
以 TP=4 makespan=rank1 为例：
- 上限估算下界区间：
  - 热读下界：`T_min_hot = 30.263/10.910 = 2.774s`
  - 冷读下界：`T_min_cold = 30.263/5.981 = 5.060s`
- 实测 makespan `T(total_ready)=5.99s`（约 **1.6×**）

差距主要来自两类“非纯带宽因素”：
1) **计划解析/分组开销**：`T(get)≈0.63s`（这部分在更小模型或更快 IO 下会变得更显著）  
2) **流水线未完全重叠**：staging 读 + pack 目前以“chunk→pack→sync”为主，仍有进一步 overlap 的空间（例如 staging 双缓冲、让下一块 IO 与上一块 pack 并行）。

#### 读放大（为何 C 比 B 多读，但更快）
- TP=4：`bytes(disk)/bytes(output)=30.263/15.257≈1.98×`
- TP=2：`bytes(disk)/bytes(output)=40.523/30.520≈1.33×`

解释：
- 这是 axis=1 列切片在 row-major 文件布局下的“不可避免代价”：要把碎片化的小段读合并为连续读，就必须读一个包含间隙的连续超集。
- C 用 ~1.3–2.0× 的读放大，换来了接近带宽上限的吞吐（从 B 的 0.3–0.6 GiB/s 提升到 9 GiB/s 级别）。

### 6.4 Strategy D：预物化（materialize once, load many）——把 C 的读放大“固化掉”

核心思路：
- 第一次加载时仍用 C（因为它能把碎片化读变成顺序读+GPU pack），但把最终 output layout **落盘为每个 rank 一个连续文件**。
- 后续加载时不再需要 staging/pack，也不再有 1.3–2.0× 的读放大：直接顺序读 `bytes(output)` 即可，理论上可以逼近冷读端到端上限 `~5.981 GiB/s`。

#### D.1 生成的产物（TP=4）

产物目录（按你的要求落在模型目录内）：`/mnt/host0/Qwen2.5-32B-Instruct/tensorcast_materialized/tp4/`
- `rank0.bin` / `rank0.meta.json`
- `rank1.bin` / `rank1.meta.json`
- `rank2.bin` / `rank2.meta.json`
- `rank3.bin` / `rank3.meta.json`

每个 rank 的 `output_bytes` 都是 `16382928896`（= `15.257 GiB`），总计 `61.027 GiB`（4 rank 合计）。

生成日志：
- `/tmp/tensorcast_materialize_d_tp4_rank0.log`
- `/tmp/tensorcast_materialize_d_tp4_rank1.log`
- `/tmp/tensorcast_materialize_d_tp4_rank2.log`
- `/tmp/tensorcast_materialize_d_tp4_rank3.log`

说明：materialize 的一次性成本包含 “Strategy C（读 + pack）” + “GPU→host D2H + write(2) 落盘”；这个成本只在首次生成时支付。

补充：本次 `materialize_d` 的 D2H+write 吞吐只有 `~1.3–1.5 GiB/s`，主要原因是实现选择了“单缓冲 + 每 chunk `cudaMemcpyAsync(D2H)` 后立即 `cudaStreamSynchronize` + `pwrite(2)` + `fsync(2)`”的最保守路径（几乎没有 overlap）。如果要优化首次生成成本，优先方向是：
- staging 双缓冲（让 D2H 与 write 重叠）
- 把 `fsync` 放到批次末尾或用更合适的 durability 策略
- 若平台支持，评估 GPUDirect Storage（直接 GPU→NVMe，避免 D2H）

#### D.2 单 rank 冷读加载（O_DIRECT，接近磁盘上限）

用 `--mode=materialized_disk_baseline --disk_io_mode=direct` 从 `rankX.bin` 读取 `bytes(output)` 并写入 GPU：
- rank0：`/tmp/tensorcast_d_load_tp4_rank0_cold.log` → `5.807 GiB/s`（2.627s）
- rank1：`/tmp/tensorcast_d_load_tp4_rank1_cold.log` → `5.976 GiB/s`（2.553s）
- rank2：`/tmp/tensorcast_d_load_tp4_rank2_cold.log` → `5.847 GiB/s`（2.610s）
- rank3：`/tmp/tensorcast_d_load_tp4_rank3_cold.log` → `6.033 GiB/s`（2.529s）

这与冷读端到端基线 `5.981 GiB/s`（`safetensors_o_direct_disk_baseline`）基本一致：D 的“后续加载”已经逼近磁盘冷读上限。

#### D.3 TP=4 并发冷读加载（4 rank 同时读同一块 NVMe）

并发 4 个进程同时读 4 个 `rankX.bin`（每个进程绑定一个 GPU），磁盘带宽会被 4 个 rank 平分：
- 日志：
  - `/tmp/tensorcast_d_load_tp4_concurrent_rank0.log`
  - `/tmp/tensorcast_d_load_tp4_concurrent_rank1.log`
  - `/tmp/tensorcast_d_load_tp4_concurrent_rank2.log`
  - `/tmp/tensorcast_d_load_tp4_concurrent_rank3.log`
- 结果（四个 rank 几乎一致）：
  - 单 rank：`~1.49 GiB/s`，`~10.23s`
  - 聚合：`(4 * 15.257 GiB) / 10.23s ≈ 5.96 GiB/s`（≈ 冷读端到端上限 `5.981 GiB/s`）

关键结论：在“单块 NVMe + 多 rank 并发读”的前提下，D 的后续加载 makespan 基本由 **磁盘冷读上限**决定：
- 理论下界：`61.027 GiB / 5.981 GiB/s = 10.204s`
- 实测 makespan：`~10.23s`（几乎贴近下界）

对比（为什么 D 对“真实 TP 并发冷读”更有意义）：
- C 在 TP=4 时每 rank `bytes(disk)≈30.263 GiB`（读放大≈1.98×），如果 4 个 rank **同时**从同一块 NVMe 冷读，磁盘总读量会变成 `~121.052 GiB`，理论下界约 `121.052/5.981 = 20.24s`。
- D 把总读量固定为 `bytes(output_total)=61.027 GiB`，因此理论下界直接减半到 `~10.20s`，并且实测已经贴近该下界。

这也解释了 D “理论最优”的意义：它把问题从“访问形态导致的 IOPS/碎片化/读放大”收敛为“顺序读带宽”问题，并且在本机上已经打到冷读带宽的天花板。

### 6.5 Strategy C_host_pack：H2D 减少了，但 CPU pack 取代 GPU pack 成为瓶颈

以本次对照实验（`/mnt/host0/Qwen2.5-32B-Instruct/tensorcast_bench_logs/20260119_host_pack_compare/`）为例：

- TP=4：
  - C：`bytes(h2d)=30.258GiB`，但 `T(pack)≈0.01s`（GPU `cudaMemcpy2DAsync(D2D)` pack 基本“免费”）
  - C_host_pack：`bytes(h2d)=15.258GiB`（理论上 H2D 时间可减半），但引入 `T(pack)≈0.90–0.94s`
  - 观察到 `T(commit)` 确实下降（约 `4.78–4.81s` → `4.20–4.45s`），但节省量（`~0.4–0.6s`）小于新增 CPU pack（`~0.9s`），因此 makespan 反而上升。

- TP=2：
  - C_host_pack 只减少了 `~10GiB` 的 H2D（40.5→30.5GiB），但 CPU pack 需要搬 `~30.5GiB`，`T(pack)=1.5–1.8s`，因此退化更明显。

瓶颈判断（为什么会这样）：
- 在当前实现里，CPU pack 本质是“DRAM→pinned 的 memcpy（按行拷贝）”，吞吐落在 `~16–20 GiB/s`，接近 `safetensors_dram_mirror_host_baseline` 测到的 userspace memcpy 上限量级；因此它很容易成为新增的主瓶颈。
- 反过来，GPU pack（C 的 staged 路径）非常快：因为它在 GPU 内完成（HBM + copy engine），且通过 `cudaMemcpy2DAsync` 合并了大量小拷贝调用，成本几乎可以忽略。

工程含义：
- **默认仍推荐 Strategy C（GPU staging + D2D pack）**：它把最重的“scatter/pack”留在 GPU 内完成，通常更稳。
- C_host_pack 更像一个“特殊条件下的 trade-off/兜底”：当 staging 显存不足、或 H2D/NUMA 异常导致 PCIe 变成硬瓶颈时，才可能出现净收益。

## 7. 结论与建议

### 7.1 结论（按 TP）
- **TP=1**：所有策略都基本是“读全 payload”，性能接近 NVMe→GPU 上限；差别不大。
- **TP=2/4**：
  - **B**：严重偏离上限（~25×），根因是 axis=1 引发的碎片化小读。
  - **A**：读全 payload 导致“理论下限”就偏高；但 A 的 pack 已通过 `cudaMemcpy2DAsync` 合并达到近似最优（TP=4 pack 3.36s → 0.02s）。
  - **C**：综合最优，且关键路径已回到带宽上限附近；仍有约 1.3–1.6× 的进一步优化空间（主要是 overlap 与 CPU/同步开销）。
  - **C_host_pack（对照）**：能显著降低 `bytes(h2d)`，但在本模型的 TP=2/4 实测中，CPU pack 变成新瓶颈，整体更慢；更适合作为“显存不足/H2D 异常时的 trade-off/兜底”。
  - **D**（预物化）：如果你会重复加载同一个 `loading-meta.json`（相同 TP/同一份计划），D 的“后续加载”可以把问题直接收敛为“顺序读带宽”，并且在本机上已经基本打到冷读端到端上限；代价是首次生成需要额外的 D2H+落盘成本与磁盘空间。
  - **集中读取 + NVLink 分发/去重（在线版的“减少总读量”）**：在“单 NVMe + 多 rank 并发冷读”场景，理论最大收益基本等于 Strategy C 的总读放大（TP=2 约 `1.33×`，TP=4 约 `1.98×`），上限接近 D 的后续加载（`~10.2s`）；但在热 cache/本机并发条件下，单一 reader 可能丢掉“多进程并行 pread”带来的 host 侧吞吐，需要引入按 socket 分区的 reader（NUMA-aware）与更强 overlap 才能稳定获益。

### 7.2 如果目标是进一步逼近上限（优先级建议）
1) **面向 C：做 IO 与 pack 的更强重叠**（双 staging buffer，减少每个 chunk 的同步点）  
2) **面向 C：降低计划/调度开销**（缓存 plan 解析结果；减少 per-tensor/ per-chunk 的固定成本）  
3) **面向 D：降低首次 materialize 成本**（D2H+write overlap、减少同步点；或用 GDS）  
4) **面向整体：建立“冷/热读”两套基线**（必要时 drop_caches；并记录磁盘/CPU负载）以更准确评估离上限距离  
5) **面向 A：若要在 TP>1 追上 C，必须减少读入字节**（否则 IO 下限过高）
