# Summary

This note records the host-local evidence used to close the remaining `0108`
ordinary-path scope on the current local machine.

The packet is intentionally trace-backed rather than mounted-serving-backed:

- the workload comes from `internal-vllm`'s current TP4 trace-plan output on
  `/mnt/step3-alignment/inference/Qwen2.5-32B-Instruct`,
- the benchmark contract is produced by lowering that trace output through
  [tools/trace_plan_to_load_plan.py](/data/workspace/tensorcast-280/tools/trace_plan_to_load_plan.py),
- the measurements focus on the `0108` owner boundary:
  ordinary host-local `GPU <- DISK` executor shape,
- and serving-ready closure remains owned by `0112` plus downstream
  `internal-vllm` docs.

# Scope

In scope:

- host-local ordinary-path executor evidence for `0108`,

  same trace-derived workload,

# Workflow

## 1. Emit TP4 trace plans from `internal-vllm`

Start a local daemon with the existing serving config shape, but use a local
temporary config that:

- changes `server.storage_path` and trusted-root scope to
  `/mnt/step3-alignment/inference`,
- keeps `enable_local_batched_disk_load=true`,
- and disables owner-file collective so host-local evidence stays on the
  ordinary-path scope.

The local run used:

```bash
source /data/workspace/internal-vllm/.venv/bin/activate
cd /data/workspace/internal-vllm

LD_LIBRARY_PATH=/data/cuda/compat:/data/cuda/cuda-12.8/lib64:/usr/local/nvidia/lib64 \
tensorcast-cli daemon start --blocking \
  --config /tmp/0108-qwen25-daemon-config.yaml \
  --global-store-mode start
```

Then run `vllm serve` only long enough to emit the trace-plan dumps:

```bash
source /data/workspace/internal-vllm/.venv/bin/activate
cd /data/workspace/internal-vllm

LD_LIBRARY_PATH=/data/cuda/compat:/data/cuda/cuda-12.8/lib64:/usr/local/nvidia/lib64 \
NCCL_DEBUG=WARN \
CUDA_VISIBLE_DEVICES=0,1,2,3 \
vllm serve /mnt/step3-alignment/inference/Qwen2.5-32B-Instruct \
  --port 8020 \
  --served-model-name qwen2.5-32b-tc-trace \
  --tensor-parallel-size 4 \
  --load-format tensorcast \
  --gpu-memory-utilization 0.70 \
  --max-model-len 1024 \
  --enforce-eager \
  --model-loader-extra-config '{"tensorcast_init_mode":"connect","tensorcast_show_daemon_logs":true,"tensorcast_enable_runtime_binding":true,"tensorcast_debug_path":"/tmp/0108-qwen25-trace","tensorcast_collective_policy":"disable_collective"}'
```

This run emitted:

- `/tmp/0108-qwen25-trace/trace_plan/tensorcast_trace_plan_tp0_pid1424563.json`
- `/tmp/0108-qwen25-trace/trace_plan/tensorcast_trace_plan_tp1_pid1424564.json`
- `/tmp/0108-qwen25-trace/trace_plan/tensorcast_trace_plan_tp2_pid1424565.json`
- `/tmp/0108-qwen25-trace/trace_plan/tensorcast_trace_plan_tp3_pid1424566.json`

The service later exited during worker bring-up; that later failure is not used
as `0108` acceptance input.

# Conclusion

This packet is sufficient to close the remaining `0108` host-local ordinary-path
work on the current local workload family.

Concretely:

- the current host-local TP4 trace-derived workload is reproducible,
- the dedicated tensor-aware local path (`strategy=c`) is clearly better than
  the generic-like fragmented path (`strategy=b`),
- the `strategy=c` numbers are also within or better than the currently
  available local `safetensors` / `fastsafetensors` data-plane references on
  this host,

  this evidence.
